# spire (squawk SPIRE reference deployment)

Thin Helm wrapper around the upstream **spiffe/helm-charts-hardened `spire`**
chart. This chart does **not** hand-roll any spire-server/spire-agent
manifests — it declares the upstream chart as a pinned dependency
(`Chart.yaml`) and overrides only the settings squawk needs (`values.yaml`).

**Prerequisite this chart does not install:** `spire-crds` (separate chart,
`https://spiffe.github.io/helm-charts-hardened/`, version `0.5.0` per the

release before this chart, because Helm does not manage CRD upgrades inside
a regular chart's lifecycle. See Install order below.

## Install order

Run against the target cluster context explicitly (`--kube-context`), never
the ambient/global context — see `devops-kubernetes.md`.

```bash
# 1. CRDs first, own release, own step — always before/separate from spire itself
helm upgrade --install spire-crds spire-crds \
  --repo https://spiffe.github.io/helm-charts-hardened/ \
  --version 0.5.0 \
  --namespace spire-server --create-namespace \
  --kube-context <context>

# 2. This wrapper chart (pulls in the pinned spire chart via Chart.lock)
cd k8s/helm/spire
helm dependency build   # verifies Chart.lock digest, populates charts/*.tgz (gitignored)
helm upgrade --install spire . \
  --namespace spire-server \
  --kube-context <context>
```

Do this once per cluster (alpha/beta/gamma/prod each get their own SPIRE
install — trust domain `spiffe://penguintech.io` is shared, but SVIDs are
cluster-local). Confirm both spire-server and spire-agent (DaemonSet) pods
are `Running` before moving on.

## Registering squawk workload entries

`spire-server.controllerManager.enabled` is `true` upstream by default, so
this deployment already runs `spire-controller-manager`, which watches
`ClusterSPIFFEID` custom resources and auto-registers matching pods — no
manual `spire-server entry create` needed. Register squawk's DNS/DHCP/NTP
servers by applying a `ClusterSPIFFEID` per service (in the SPIRE
`spire-server` namespace or wherever the CRDs were installed), matching the
squawk chart's pod labels:

```yaml
apiVersion: spire.spiffe.io/v1alpha1
kind: ClusterSPIFFEID
metadata:
  name: squawk-dns-server
spec:
  className: spire-server  # matches this chart's controller-manager className
  spiffeIDTemplate: "spiffe://penguintech.io/{{ .PodMeta.Namespace }}/dns-server/{{ .PodMeta.Name }}"
  podSelector:
    matchLabels:
      app.kubernetes.io/name: squawk
      app.kubernetes.io/component: dns-server
  namespaceSelector:
    matchLabels:
      kubernetes.io/metadata.name: squawk
```

Repeat with `app.kubernetes.io/component: dhcp-server` / `ntp-server` for the
other two servers. The resulting SPIFFE ID must match the
`spiffe://<trust_domain>/<env>/<service>/<instance>` scheme validated by
`manager/backend/app/services/spiffe.py` — adjust `spiffeIDTemplate` to embed
the actual environment segment (alpha/beta/gamma/prod) if it doesn't already
come from `.PodMeta.Namespace` in your layout, since squawk's namespace is
the product name only (`squawk`), not environment-suffixed (see
`devops-kubernetes.md`).

## Configuring the mesh/ingress to forward + strip XFCC

SPIRE issues X.509-SVIDs; it does not by itself put anything in an HTTP
header. The manager's SPIFFE auth path
(`manager/backend/app/services/spiffe.py`,
`docs/ENTERPRISE_SECURITY.md` §6) reads the peer identity from the
`X-Forwarded-Client-Cert` (XFCC) header, which must be populated by whatever
terminates mTLS in front of the manager — a service mesh sidecar (Envoy,
Istio) or an mTLS-terminating gateway. **No service mesh chart ships in this
repo today** — provisioning one (or configuring an existing ingress/gateway
to do SPIFFE-based mTLS + XFCC injection) is a separate, required piece of
work before `SPIFFE_ENABLED=true` is safe to flip. Whichever proxy you use:

1. Terminate mTLS using the SPIRE-issued SVID (via the SPIFFE Workload API
   socket — see the upstream chart's own `README.md` "Usage" section for the
   CSI-driver volume mount pattern every workload needs).
2. Inject the verified peer SPIFFE ID into the `X-Forwarded-Client-Cert`
   header (or whatever header name `SPIFFE_XFCC_HEADER` is set to) on
   requests forwarded to the manager.
3. **Strip any inbound copy of that header from outside the mesh** — XFCC is
   a client-supplied header; if an external caller can set it directly and
   reach the manager, they can forge any server identity. This is the exact
   trust-boundary concern documented in `docs/ENTERPRISE_SECURITY.md` §6 as
   the reason `SPIFFE_ENABLED` defaults to `false`.
4. Ensure the manager is **not** directly reachable bypassing the mesh/proxy
   (see the squawk chart's `networkpolicy.yml` — the manager's NetworkPolicy
   already restricts ingress to same-namespace pods only, which helps but is
   not itself an XFCC-stripping control).

## Flipping SPIFFE_ENABLED=true in the squawk chart

Today `SPIFFE_ENABLED` / `SPIFFE_TRUST_DOMAIN` / `SPIFFE_XFCC_HEADER` are
manager environment variables (see `manager/backend/app/config.py`) but are
**not yet exposed as Helm values** in `k8s/helm/squawk` — the squawk chart's
`manager-deployment.yml` doesn't source them from `.Values` yet. That wiring
is out of scope for this reference chart (which only covers the SPIRE
deployment itself); until it lands, enable the flag out-of-band once steps
1–3 above are done and verified:

```bash
kubectl --context <context> -n squawk set env deployment/manager \
  SPIFFE_ENABLED=true \
  SPIFFE_TRUST_DOMAIN=penguintech.io \
  SPIFFE_XFCC_HEADER=X-Forwarded-Client-Cert
```

Confirm dns-server/dhcp-server/ntp-server pods have the
`spiffe-workload-api` CSI volume mounted (see the upstream chart's `README.md`
"Usage" section) so they can present their SVID to the mesh, then watch
manager logs for `auth_method=spiffe` on server-token requests before
retiring the legacy per-server JWT secret.

## Clean up

```bash
helm -n spire-server uninstall spire
helm -n spire-server uninstall spire-crds
kubectl --context <context> delete crds \
  clusterfederatedtrustdomains.spire.spiffe.io \
  clusterspiffeids.spire.spiffe.io \
  clusterstaticentries.spire.spiffe.io
```
